💡 [쉽게 말하면...] 왜 파일 하나인데 conn과 SQL이 필요할까요?
  • conn (연결 배관): 파이썬 메모리와 디스크 파일 사이에 꽂아둔 "전용 빨대"입니다.
  • to_sql (밀어넣기): 내 손(RAM)에 있는 데이터프레임을 빨대를 통해 DB 창고로 밀어 넣는 것입니다 (if_exists='append'로 일별 누적).
  • read_sql (빨아들이기): DB 창고의 수백만 행 중 내가 작성한 주문서(SQL 질의문)에 맞는 것만 빨대로 쏙 빨아들여 새 DataFrame으로 가져옵니다.

🏗 append vs replace — 같은 코드, 다른 결과 (블록 누적 비주얼)
returns_new.to_sql('returns', conn, if_exists='append', index=False)

  • ›append는 기존 표를 두고 새 행만 뒤에 붙입니다.

  • ›정수끼리 나누면 파이썬3와 달리 소수점 아래가 통째로 절삭되어 0이 됩니다.
  • ›분자나 분모 중 하나에 * 1.0을 곱해 실수로 승격시키면 정상적인 비율(ROE)이 나옵니다.

💡 [쉽게 말하면...] 왜 파이썬과 다르게 0이 나올까요?
  • 파이썬3의 친절함: 5 / 2 = 2.5처럼 정수끼리 나눠도 자동으로 실수형(float)으로 바꿔줍니다.
  • SQL의 엄격함: 정수 / 정수 = 정수라는 엄격한 컴퓨터 연산 규칙을 따릅니다. 0.11에서 소수점 아래를 가위로 싹둑 잘라내고 정수 0만 남깁니다.
  • 해결 열쇠 (* 1.0): 분자나 분모 중 하나에 * 1.0을 곱해주면 컴퓨터가 "아, 이건 소수점이 필요한 실수 연산이구나!"라고 인식하여 소수점을 살려냅니다.
🗂 묶은 다음엔, 하나로 못 줄이는 값을 그대로 꺼낼 수 없다 (집계 바구니 구조도)

GROUP BY c.sector로 묶으면 한 업종에 여러 회사가 섞인다. SQLite는 에러를 내지 않고 아무 회사 이름이나 하나 골라 출력해 데이터를 심각하게 왜곡시킨다.

🚨 에러 없이 조용히 틀림
  • 전기전자 업종 평균 ROE(0.14) 옆에 "삼성전자"라는 이름이 붙는다 — 실제로는 삼성전자·SK하이닉스·삼성전기 세 회사의 평균인데, 삼성전자만의 값처럼 보인다.
더 엄격한 DB(PostgreSQL 등)는 위험한 버전을 아예 문법 에러로 차단한다 — 뒤에서 클라우드 DB로 넘어갈 때 다시 만난다.
🔗 ON이 없으면, 가능한 모든 조합(카르테시안 곱)이 나온다
SELECT c.name, f.year, f.revenue, f.net_income FROM companies AS c JOIN financials AS f ON c.code = f.code;

두 표 다 code 열이 있으니 그 열로 잇는다. 아래 인터랙티브 매칭 다이어그램으로 정상 연결선과 카르테시안 곱 그물망을 대조한다.

☁️ 같은 세 표, 클라우드에서도 같은 방법

앞선 200·300번 노트에서 SQLite에 던졌던 조회를 같은 세 표(companies·financials·returns)를 담은 클라우드 PostgreSQL(Supabase)에 이번 주 직접 다시 던진다.

SQLite는 로컬 파일에 직접 붙지만, 클라우드 DB는 왜 API 게이트웨이를 거칠까요? 아래 다이어그램에서 '주방 난입 ❌'과 '드라이브스루 ✅'의 차이를 확인하세요.

🔑 노트북에 넣어도 되는 key, 넣으면 안 되는 것
  • publishable key는 프로젝트 식별용 공개 키 — 학생 노트북에는 세 표의 SELECT 권한만 부여되어 안전하다.
  • service_role key·개인 액세스 토큰·DB 비밀번호는 절대 노트북에 적지 않는다 — 관리자 권한이다.
🆚 무엇이 다른가 — 경계 있는 연속성 (3대 차이 진단)

"거의 그대로 통한다"고 과장하면 나중에 "SQLite에서는 됐는데 왜 안 되지"를 혼자 만나게 된다. 아래 3개 버튼으로 실제 경계를 미리 확인한다.

표 값을 담을 열의 타입을 미리 정확히 지키는 습관이, SQLite에서는 "그래도 되니까" 느슨해지기 쉽다는 걸 기억해둔다.
🔬 교수가 클라우드 DB 값을 바꾸면 일어나는 일 (중앙 SSOT 동기화 구조도)

내 PC의 파일이 아니라 클라우드 DB를 바라볼 때 생기는 진짜 차이 — 교수가 데이터를 고치고 학생이 같은 코드를 재실행하는 과정을 단계별로 확인한다.

학생은 코드를 한 글자도 고치지 않고 같은 셀을 다시 실행했을 뿐인데 결과가 바뀌었다 — 중앙의 단일 진실 공급원(SSOT)을 공유하기 때문이다.
🤖 MCP — 질문을 쓰는 사람이 바뀐다 (3계층 프로토콜 구조)

MCP(Model Context Protocol)는 AI가 정해진 통로로 DB 같은 바깥 시스템에 접근하는 규약이다. 바뀐 것은 "질문을 쓰는 방법"이지 DB 자체가 아니다.

⚠️ SQL을 몰라도 된다는 뜻이 아니다
  • MCP가 대신 쿼리를 짜준다고 해도, 결과가 맞는지(ORDER BY 누락 여부, ON 누락 폭발 여부)는 SQL을 아는 사람만 검증할 수 있다 — "Trust but Verify".
