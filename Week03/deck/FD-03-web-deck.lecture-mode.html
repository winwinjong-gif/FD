같이 쓰는 사람 수 × 데이터 크기 — SQLite는 개인 분석 캐시, 회사는 하나만 쓰지 않는다

▶ 사분면 좌하 SQLite "지금 우리 자리" → 점선 화살표 따라 Supabase → 🧪 §500 열기SQLite → PostgreSQL·MySQL(회사 서버) → Supabase(클라우드) → BigQuery(대규모)분석가 계정은 대부분 읽기 전용 — 수업이라서가 아니다
📌 SQLite의 자리를 정확히
  • 개인 분석용 캐시: 중앙 저장소가 아닌 로컬 고속 작업대
  • 동시 쓰기 시 잠김: 여러 명이 동시에 쓰면 파일이 통째로 잠김
  • 읽기 전용 계정: 실무 분석가 계정도 대부분 SELECT 전용
⚠️ 흔한 오해 차단

"회사도 SQLite로 서비스 운영한다"고 오해하면 안 됩니다. 목적·규모·사용자 수에 따라 시스템을 달리 쓰는 것이 실무 표준입니다.

§600 · Part 2

"거의 그대로"에는 경계가 있다 — SQLite는 조용히 저장, PostgreSQL은 그 자리에서 멈춘다

▶ 통하는 것/다른 것 표 읽기 → 타입 경계 한 줄 예고(결과는 노트북에서)통함: SELECT·WHERE·ORDER BY·LIMIT·GROUP BY·JOIN다름: 타입 처리 · 날짜 함수 strftime ↔ date_trunc · 엄격함
그대로 통하는 것 (연속성) ✅ 경계가 다른 것 (주의점) ⚠️
SELECT · WHERE · ORDER BY · LIMIT 타입 처리: SQLite는 유연, PostgreSQL은 엄격한 타입 강제
GROUP BY · 집계 함수 (SUM, AVG) 날짜 함수: SQLite strftime ↔ PostgreSQL date_trunc
JOIN ... ON 두 표 결합 오류 대처: 조용히 저장하는가 vs 즉시 에러를 내며 멈추는가
📁 SQLite의 유연함 — 침묵하는 위험

INSERT INTO t (revenue) VALUES ('오류아님');

숫자 열(INTEGER)에 문자열을 넣어도 에러 없이 text로 조용히 저장합니다.

❓ 이 값에 + 1000 계산을 시키면 무슨 일이 생길까? (결과는 노트북 실습에서 확인)

🔒 PostgreSQL의 엄격함 — 그 자리에서 멈춤

ERROR: invalid input syntax for type integer: "오류아님"

지정된 타입과 맞지 않는 값이 들어오는 즉시 쿼리 실행을 거부하고 에러를 냅니다.

PostgreSQL 공식 문서 기준 — 이 노트에서 직접 실행한 결과는 아니다
