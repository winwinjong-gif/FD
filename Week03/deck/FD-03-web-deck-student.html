🔍 분석가의 실무 질문: 좋은 기업 선별하기

"매출이 꾸준히 늘고 있고, 같은 업종 평균보다 수익성(ROE)이 높으며, 최근 주가가 과열되지 않은 기업."

  • 기업기본 (`companies`): 종목코드, 회사명, 소속 업종
  • 재무제표 (`financials`): 분기별 매출액, 영업이익, 자본총계
  • 주가수익률 (`returns`): 일별 종가, 거래량, 기간 수익률
💡 세 데이터는 독립된 출처에서 발생하며, 종목코드(code)로 연결됩니다.
⚠️ 팀장님의 한마디: 조건 변경 시나리오
"어제 뽑은 매출 1조 원 이상 기업에서, 기준만 5,000억 원으로 낮춰 5개만 다시 뽑아와 봐."

조건 숫자 하나 바꿨을 뿐인데 발생하는 현실의 고통:

  • 수백 MB짜리 CSV 파일 3개를 처음부터 다시 디스크에서 로딩
  • 결측치 재처리 및 pd.merge() 무거운 병합 연산 재실행
  • 메모리 사용량 급증(OOM) 및 팬 소음과 함께 무기력한 대기
질문: 데이터는 그대로인데 왜 매번 파일 전체를 처음부터 뒤집어까야 할까?
Key Takeaway 데이터는 데이터베이스에 안전하게 한 번 쌓아두고, 조건이 바뀔 땐 질문(SQL) 한 줄만 던져 0.03초 만에 꺼내 씁니다. 🎯 실시간 실험실 시연 ↗ (실험 0: 루프 대조)
§100 WHY DATABASE · 5-STAGE FILE LOOP

5단계 파일 루프의 병목과 DB 엔진의 혁신

파일 방식은 조건 변경마다 전체 과정을 원점 반복하지만, DB는 질문(WHERE) 한 줄만 바뀝니다.

⚙️ 시스템 메커니즘 대조
구분 파일 (CSV) 데이터베이스
데이터 접근 전체 행 디스크 풀스캔 B-Tree 인덱스 핀포인트

속도 반응 수 분 소요 (OOM 위험) 0.03초 즉각 반환
📌 눈으로 확인할 점: 위쪽 줄기(파일)에만 되돌아가는 붉은 화살표가 존재합니다. DB는 붉은 루프 자체를 제거합니다.
Key Takeaway B-Tree 인덱스를 탑재한 DB 엔진은 수백만 행 전체를 뒤집지 않고, 조건에 맞는 5개 행만 디스크에서 집어 올립니다. 🎯 실시간 실험실 시연 ↗

📈 금융 데이터 실무 (Production Model)

쇼핑몰의 user_id가 하던 역할을 금융에서는 code가 합니다:

표 이름저장하는 데이터연결 열

financials분기실적, 매출액, 영업이익, 자본code, year, quarter

🎯 이번 주 내내 기억할 단 하나의 원칙: "두 표에 같이 들어 있는 열(code)로 잇는다!"
Key Takeaway 관계형 데이터베이스(RDBMS)의 모든 원리는 "각 표의 고유 식별자(종목코드)를 열쇠 삼아 연결한다"는 직관 하나로 통합니다.
§100 WHY DATABASE · FINTECH ARCHITECTURE

실전 핀테크 아키텍처: 토스증권 화면 뒤의 데이터 흐름

앱 화면 하나를 보여주기 위해 API 수집, 중앙 데이터베이스(SSOT), 분석 파이프라인이 결합됩니다.

💡 핀테크 아키텍처의 핵심 교훈
  • 호출 제한(Rate Limit) 방어: 외부 API는 초당 호출 횟수 제한이 있어 실시간으로 매번 찌르면 차단당합니다.
  • 배치 적재(Batch Ingestion): 정해진 시각(장마감 후)에 데이터를 한 번만 가져와 중앙 DB에 적재합니다.
  • 단일 진실 공급원(SSOT): 모바일 앱과 퀀트 분석가가 동일한 DB를 바라보므로 데이터 불일치가 0이 됩니다.
이 구조의 축소판을 오늘 내 컴퓨터(SQLite)와 클라우드(Supabase) 위에 그대로 구축합니다!
Key Takeaway 중앙 DB는 외부 API의 호출 제한을 막아주는 안전 완충재이자, 핀테크 서비스 전체의 정합성을 보장하는 심장입니다.
§100 WHY DATABASE · EXCEL VS DATABASE

엑셀 vs 데이터베이스: 금융 실무를 가르는 4대 차이

100만 행 한계를 넘어 무결성, 동시성, 자동화 파이프라인으로 나아가는 전환점입니다.

비교 축 스프레드시트 (Excel / CSV) 관계형 데이터베이스 (RDBMS)
1. 데이터 용량 최대 1,048,576행 제한. 수십만 행 이상 시 버벅거림 및 프리징 발생. 수억~수십억 행 무제한. 디스크 인덱스로 수백만 행도 0.01초 검색.
2. 무결성과 정합성 셀 단위로 아무 값이나 입력 가능. 실수로 수식이나 행을 지울 위험 상존. 스키마 제약조건(PK, FK, NOT NULL). 잘못된 데이터 유입 원천 차단.
3. 동시 다중 접근 동시에 열면 "읽기 전용" 경고. 덮어쓰기로 인한 변경 내역 소실 빈번. 트랜잭션(ACID) 지원. 수백 명이 동시에 읽고 써도 충돌 없는 데이터 보장.
4. 파이썬 자동화 수동 파일 복사, 마우스 클릭 의존. 매일 아침 수작업 반복 필요. 코드 파이프라인 직결. pd.read_sql로 매일 아침 자동 스크리닝 리포트 산출.
⚠️ 실무 금융 사고의 90%는 수동 엑셀 파일 관리에서 발생합니다

월스트리트 투자은행(JP모건 고래 참사 등)의 천문학적 손실 뒤에는 언제나 '엑셀 수식 복사 오류'나 '파일 덮어쓰기'가 있었습니다. 금융 데이터 사이언티스트가 DB를 다루는 것은 선택이 아닌 필수 생존 역량입니다.

Key Takeaway 엑셀은 사람의 최종 보고서 뷰어로 남겨두고, 데이터의 축적·정제·연산은 데이터베이스에 일임합니다.

§200 SQLITE BASICS · CONNECT & CONN

내 컴퓨터 안의 무설치 DB: sqlite3.connect

별도의 DB 서버 데몬 설치 없이 파일 하나(.db)로 작동하는 가장 우아한 임베디드 RDBMS입니다.

🔌 파이썬 표준 라이브러리 sqlite3

별도 패키지 설치(`pip install`)조차 필요 없습니다. 파이썬에 기본 탑재되어 있습니다.

import sqlite3
import pandas as pd

# DB 파일과 파이썬 파이프라인 연결
conn = sqlite3.connect('data/market_data.db')

print("DB 연결 성공:", conn)
DB 연결 성공: [sqlite3.Connection object at 0x10a2b4...]
🏗️ 연결자(conn)와 파일 구조의 비밀
  • 단일 파일 완결성: market_data.db 파일 하나 안에 모든 테이블, 인덱스, 메타데이터가 바이너리로 압축 저장됩니다.
  • 이식성의 극치: 이 파일 하나만 카톡이나 이메일로 팀원에게 보내면, 상대방도 즉시 동일한 쿼리를 0.001초 만에 실행할 수 있습니다.
  • 서버리스(Serverless): 백그라운드 프로세스나 포트(Port) 충돌이 전혀 발생하지 않아 초보자 학습 및 단일 분석에 최적입니다.
💡 연결자(conn)의 역할: 파이썬 인터프리터와 SQLite C-엔진 사이를 이어주는 고속 데이터 고속도로입니다.
Key Takeaway SQLite는 파일 하나로 RDBMS의 모든 강력함(SQL, B-Tree 인덱스, 트랜잭션)을 누릴 수 있는 최고의 실무 분석 도구입니다. 🎯 실시간 실험실 시연 ↗ (실험 1: 적재·인출)
§200 SQLITE BASICS · INGESTION (TO_SQL)

데이터를 넣는 일: df.to_sql (append vs replace)

새 거래일 데이터를 누적할 때는 append를, 스키마 재구축이 아니라면 replace의 참사를 피하세요.

✅ 실무 표준: if_exists='append' (누적 적재)

기존 테이블의 과거 데이터는 그대로 보존하고, 새 거래일/새 분기 데이터만 뒤에 이어 붙입니다.

# 새 영업일 주가 데이터를 기존 테이블에 안전하게 누적
df_today.to_sql(
  'returns',
  conn,
  if_exists='append',
  index=False
)
💡 실무 배치 파이프라인의 99%는 이 방식으로 매일 장마감 시 데이터를 누적합니다.
❌ 주의 위험: if_exists='replace' (전체 소실)

기존 테이블을 통째로 DROP TABLE하고, 지금 들고 있는 DataFrame으로 덮어씁니다!

# ⚠️ 치명적 실수: 오늘 하루 치 주가를 넣으려다
# 과거 10년 치 데이터 전체가 영구 소실됨!
df_today.to_sql(
  'returns',
  conn,
  if_exists='replace',
  index=False
)
⚠️ 스키마를 처음부터 완전히 다시 만들 때가 아니면 'replace'는 봉인합니다!
Key Takeaway 운영 DB에 replace를 던지는 순간 과거 데이터는 영원히 증발합니다 — 항상 append를 기본 옵션으로 삼으세요. 🎯 실시간 실험실 시연 ↗
§200 SQLITE BASICS · RETRIEVAL (READ_SQL)

데이터를 꺼내는 일: pd.read_sql과 DataFrame 변환

DB에 담긴 테이블 목록을 확인하고, 쿼리 결과를 판다스 데이터프레임으로 바통 터치받습니다.

📋 sqlite_master로 보유 테이블 확인
# DB 내 모든 테이블 이름 조회
query = """
SELECT name
FROM sqlite_master
WHERE type = 'table'
"""
pd.read_sql(query, conn)
       name
0  companies
1  financials
2    returns
⚡ pd.read_sql의 동작 파이프라인
  • SQL 파싱: 쿼리 문자열이 SQLite C-엔진으로 전송되어 문법을 파싱합니다.
  • 인덱스 추출: 조건에 맞는 행들만 디스크 바이너리에서 메모리로 추출합니다.
  • DataFrame 즉시 생성: 추출된 튜플(행)들이 판다스 인메모리 DataFrame으로 즉시 래핑됩니다.
핵심: 파이썬 반복문(for row in cursor:)을 직접 돌릴 필요 없이, 판다스가 C 레벨에서 최적화된 속도로 DataFrame을 만들어 줍니다.
Key Takeaway pd.read_sql(query, conn)은 DB 엔진의 검색 결과와 판다스의 분석 엔진을 단 1줄로 이어주는 마법의 통로입니다.
§300 CORE SQL · 1. FILTERING (WHERE)

조건으로 거르기: WHERE와 텍스트 종목코드 따옴표

🎯 다중 조건 필터링 (AND)
# 2025년 매출액 3,000억 초과 기업만 필터링
query = """

⚠️ 치명적 함정: 종목코드 따옴표 누락!

한국 거래소의 종목코드는 6자리 TEXT(문자열) 컬럼입니다.

-- ❌ 오답: 앞자리 0 두 개가 소실되어 검색 실패!
WHERE code = 5930

-- ✅ 정답: 문자열 따옴표를 반드시 감싸준다!

Key Takeaway WHERE 절은 디스크에서 행을 읽는 순간 필요 없는 데이터를 잘라내어 메모리 낭비를 원천 차단합니다. 🎯 실시간 실험실 시연 ↗ (실험 2: 5대 문법 랩)

§300 CORE SQL · 3. DERIVED METRICS

새로운 지표 만들기: 계산열(ROE)과 정수 나눗셈 함정

SQLite의 정수 나눗셈 소수점 증발 함정을 피하고, 반올림(ROUND)으로 의미 있는 재무 지표를 만듭니다.

🧮 파생 계산열: 자기자본이익률 (ROE)
# 순이익 / 자본총계 = ROE (퍼센트 및 소수점 2자리)
query = """
SELECT code,
       ROUND(net_income * 100.0 / total_equity, 2) AS roe
FROM financials
WHERE year = 2025
ORDER BY roe DESC
LIMIT 5
"""
pd.read_sql(query, conn)
     code    roe
0  000660  24.12
1  005930  11.45
2  035420   9.20
⚠️ 정수 나눗셈 함정 (Integer Division)

SQLite를 포함한 대다수 SQL 엔진은 정수 / 정수 = 정수로 계산합니다!

-- ❌ 참사: 3 / 4 계산 시 0.75가 아닌 0으로 소수점 버림!
net_income / total_equity  ➔ 전부 0으로 반환됨!

-- ✅ 해결: 실수 리터럴(100.0 또는 1.0)을 먼저 곱한다!
net_income * 100.0 / total_equity  ➔ 정상 부동소수점 연산
계산열이 자꾸 0으로 나온다면 가장 먼저 실수(1.0) 곱하기를 빠뜨렸는지 점검하세요!
Key Takeaway SQL 계산식에서는 반드시 1.0이나 100.0을 곱해 명시적 실수 연산을 강제하고, AS 별칭으로 새 컬럼명을 붙여줍니다.
§300 CORE SQL · 4. AGGREGATION (GROUP BY)

업종별로 묶어 요약하기: GROUP BY와 집계 함수

수천 개 종목을 전기전자, 화학, 자동차 등 업종 바구니로 묶어 산업군 평균 통계를 한눈에 조망합니다.

📊 업종별 평균 매출 & 기업 수 집계
# 업종별 기업 수(COUNT)와 평균 매출(AVG) 산출
query = """
SELECT c.sector,
       COUNT(*) AS n_companies,
       ROUND(AVG(f.revenue), 0) AS avg_revenue
FROM companies c
JOIN financials f ON c.code = f.code
WHERE f.year = 2025
GROUP BY c.sector
ORDER BY avg_revenue DESC
"""
pd.read_sql(query, conn)
🧺 바구니에 담아 압축하는 메커니즘
  • 바구니 분류: GROUP BY sector에 의해 '전기전자', '자동차', '화학' 바구니가 생성됩니다.
  • 바구니 안 집계: 각 바구니 안에 들어온 행들의 매출을 더하고 나눠 AVG()와 COUNT()를 1행씩으로 요약합니다.
  • 거시적 비교: 2,000개 개별 종목 대신 15개 업종별 통계 행으로 압축되어 산업 간 비교가 명확해집니다.
💡 주의: GROUP BY에 적지 않은 일반 열(예: c.name)은 SELECT에 함부로 쓰지 않는다 (바구니 안의 어떤 회사명을 보여줘야 할지 DB가 알 수 없음).
Key Takeaway GROUP BY는 방대한 금융 마이크로 데이터를 거시적 매크로 통계(업종별 평균·합계)로 압축해 주는 요약기입니다.
§300 CORE SQL · 5. MULTI-TABLE JOIN

흩어진 두 표 잇기: JOIN의 메커니즘과 공통 열

기업 기본정보와 재무제표를 종목코드(code)로 이어 실무에서 원하는 완전한 단일 표를 만듭니다.

🔗 실전 조인 구문
SELECT c.name, c.sector, f.revenue
FROM companies c
JOIN financials f
  ON c.code = f.code
WHERE f.year = 2025
  • 별칭(Alias): companies c, financials f처럼 약어를 주면 쿼리가 깔끔해집니다.
  • ON의 중요성: ON c.code = f.code가 누락되면 모든 행이 곱해져 시스템이 뻗어버립니다.
Key Takeaway JOIN은 두 표 사이에 공통으로 존재하는 식별자(code)를 다리 삼아, 필요한 정보만 한 행으로 이어 붙입니다. 🎯 실시간 실험실 시연 ↗
§300 CORE SQL · ERROR DEBUGGING

SQL 에러 디버깅: 가장 흔한 3대 오류와 해결법

빨간색 에러 메시지를 만났을 때 당황하지 않고 원인을 짚어내는 체크리스트입니다.

① no such table
OperationalError: no such table: financial

원인: 테이블 이름의 오타입니다. 복수형 financials를 단수형 financial로 잘못 썼을 때 발생합니다.

해결: sqlite_master로 정확한 테이블명을 재확인합니다.
② syntax error
OperationalError: near "FROM": syntax error

원인: SQL 문법 오타입니다. SELECT 문 마지막 열 뒤에 불필요한 쉼표(,)를 붙였거나 키워드 순서가 꼬였을 때 생깁니다.

해결: 에러가 발생한 단어 직전의 쉼표나 따옴표를 지웁니다.
③ no such column
OperationalError: no such column: code

원인: 컬럼명 오타이거나, JOIN 시 두 표 모두에 code가 들어있어 어느 표의 것인지 모호할 때 발생합니다.

해결: c.code처럼 테이블 별칭을 명시적으로 붙여줍니다.
Key Takeaway 에러 메시지는 실패의 증거가 아니라 길을 안내하는 나침반입니다 — 첫 줄의 에러 키워드부터 확인하세요.

보안과 안정성: SQL Injection 방지와 파라미터 바인딩

파이썬 f-string으로 쿼리에 값을 직접 끼워 넣지 말고, 안전한 params 바인딩을 사용하세요.

❌ 지양: f-string 직접 문자열 결합
code = "005930"
# ⚠️ 따옴표 누락 위험 및 SQL Injection 보안 취약점
query = f"SELECT * FROM companies WHERE code = '{code}'"
pd.read_sql(query, conn)

만약 사용자 입력값에 악의적인 ' OR '1'='1이나 DROP TABLE이 들어가면 데이터가 통째로 털리거나 날아갈 수 있습니다.

✅ 권장: params 파라미터 바인딩
code = "005930"
# 플레이스홀더(:code) 사용
query = "SELECT * FROM companies WHERE code = :code"
pd.read_sql(query, conn, params={'code': code})

DB 엔진이 SQL 명령어 구조와 입력 데이터 값을 완전히 분리하여 해석하므로, 어떤 이상한 값이 들어와도 안전하게 방어됩니다.

Key Takeaway 파라미터 바인딩(params)은 따옴표 실수를 방지하고 악의적인 공격을 차단하는 실무 엔지니어링의 기본입니다.

§600 CLOUD DB · DRIVE-THRU SECURITY

왜 DB를 외부에 열지 않을까? API 게이트웨이 드라이브스루

원격 DB를 인터넷에 그대로 노출하면 0.1초 만에 날아갈 수 있으므로, 안전한 주문 창구를 방패로 둡니다.

🍔 드라이브스루 보안 메타포
비유 (드라이브스루)클라우드 시스템 실체보안 역할
🚗 손님 차량 학생 VS Code / 로컬 환경 데이터를 요청하는 클라이언트
🎫 영수증 / 쿠폰 publishable key 읽기 전용(SELECT) 인증 티켓
🛡️ 주문 창구 API 게이트웨이 & RLS 티켓 검사 ➔ 쓰기/삭제 차단 ❌
🔒 보호된 주방 PostgreSQL 중앙 DB 외부 인터넷 차단, 데이터 보존
손님이 직접 주방에 들어와 냄비를 뒤엎을 수 없듯, 학생 코드가 원격 DB를 직접 건드리지 못하게 게이트웨이가 차단합니다.
⚠️ 노트북에 넣어도 되는 키 vs 넣으면 안 되는 키
✅ 노트북에 넣어도 되는 것: publishable key

프로젝트 식별용 공개 키. Row Level Security(RLS)가 걸려 있어 세 표의 SELECT(읽기)만 허용되며, 데이터 수정·삭제는 원천 차단됩니다.

❌ 절대 코드/노트북에 넣으면 안 되는 것: service_role key

관리자 마스터 키! 깃허브나 노트북에 올라가는 순간 누구든 DB 전체를 지우거나 해킹할 수 있습니다. 비밀번호와 함께 절대 노출 금지!

Key Takeaway API 게이트웨이와 읽기 전용 키(RLS)는 전 세계에 노출된 클라우드 DB의 무결성을 지키는 핵심 방패입니다.
§600 CLOUD DB · AI & MCP AGENT

자연어로 DB를 조회하는 AI: MCP와 사람의 검증 책임

AI가 Model Context Protocol로 DB에 직접 접근하지만, 쿼리 결과의 타당성은 사람이 검증해야 합니다.

🤖 Model Context Protocol (MCP) 구조

"2025년 ROE 15% 넘는 반도체 기업 뽑아줘"라고 자연어로 말하면:

1. 스키마 파악
테이블/컬럼 구조 읽기
2. SQL 자동 작성
JOIN & WHERE 생성
3. DB 엔진 실행
API로 쿼리 전송
4. 한국어 요약
답변 및 표 제시
⚖️ 인간 분석가의 고유한 검증 책임
  • 환각(Hallucination) 위험: AI가 쿼리를 짤 때 엉뚱한 컬럼을 나눗셈하거나, INNER JOIN 대신 잘못된 조인을 걸어 행이 누락될 수 있습니다.
  • 비즈니스 논리 검증: 산출된 숫자가 상식적인 금융 범위(예: ROE가 10,000%로 튀거나 매출이 음수)에 있는지 판단하는 것은 전적으로 사람의 몫입니다.
  • 최종 결정권자: "AI가 뽑아준 표니까 맞겠지"라는 태도는 실무에서 치명적인 오판을 낳습니다.
📌 오늘 SQL 5대 문법을 배운 이유: AI가 짠 쿼리를 읽고 검증할 수 있는 눈을 갖추기 위함입니다!
Key Takeaway AI는 강력한 코딩 조력자이지만, 도출된 쿼리의 정합성과 금융 논리를 최종 검증하는 주체는 분석가 자신입니다.
