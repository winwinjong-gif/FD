§100 기본적 분석 · 주가와 실적

"요즘 이 종목 오른다던데, 사도 될까?" — 주가는 시장의 기대, 재무제표는 실적

⚠️ 주가만 보고 사면 왜 위험한가?

친구가 최근 며칠 계속 오른다고 추천합니다. 하지만 오늘 주가는 오늘 시장이 매긴 가격일 뿐입니다.

시장의 기대(주가) vs 회사의 실적(재무제표)
실적이 늘어도 주가가 그보다 훨씬 더 올라 있으면 비싸게 사는 것이고, 실적이 탄탄한데 주가가 그대로라면 싸게 살 기회입니다.
이 둘이 항상 일치하지 않기 때문에, 우리는 재무제표 원본 숫자를 직접 열어 체력을 확인해야 합니다.
💡 실적을 모르면 "지금 가격이 비싼지 싼지" 자체를 판단할 수 없습니다.

§100 재무제표의 역할 · 건강검진표

재무상태표는 시점의 스냅샷(자산=부채+자본), 손익계산서는 기간의 흐름표(매출→이익)

🩺 재무상태표 (Balance Sheet)
시점 스냅샷
특정 시점에 회사가 무엇을 가졌고(자산), 얼마를 빚졌고(부채), 내 몫이 얼마인지(자본) 찍은 사진입니다.
자산(566.9조) = 부채(130.6조) + 자본(436.3조) — 항상 성립하는 기본 항등식
📈 손익계산서 (Income Statement)
기간 흐름표
1년 동안 물건을 팔아(매출) 비용을 빼고 최종적으로 얼마가 남았는지(순이익) 보여주는 흐름표입니다.
삼성전자 2025 최종 당기순이익 = 45.2조 원 — 오늘 모든 실습의 절대 기준값!

§100 지표 해석 · 세 개의 렌즈

PER·PBR·ROE — 같은 재무제표를 해석하는 서로 다른 세 가지 질문

ROE 자기자본이익률
"내 돈(자본)으로 1년에 얼마나 벌었나?"
당기순이익 ÷ 자본총계
= 45.2조 ÷ 436.3조
≈ 10.4%

자기자본 100원을 굴려 1년에 10.4원을 남겼다는 뜻입니다. 기업의 수익 창출 능력을 나타냅니다.

질문: 이 회사는 돈을 잘 굴리는가?
PER 주가수익비율
"회사가 번 이익에 비해 주가가 몇 배인가?"
시가총액 ÷ 당기순이익
= 401.3조 ÷ 45.2조
≈ 8.88배

현재 시가총액이 연간 순이익의 약 9배 수준입니다. 배수가 낮을수록 번 돈에 비해 싸게 거래됩니다.

질문: 이익에 비해 주가가 비싼가, 싼가?
PBR 주가순자산비율
"장부상 순자산(자본)에 비해 몇 배인가?"
시가총액 ÷ 자본총계
= 401.3조 ÷ 436.3조
≈ 0.92배

1보다 작으면 시장에서 매긴 몸값(시총)이 장부상 순자산보다 작다는 의미로 저평가 신호로 쓰입니다.

§200 API & HTTP · 기본 두 동작

API는 복잡하지 않다 — 조회(GET: 읽기)와 저장(POST: 쓰기) 두 동작이 전부다

🔌 컴퓨터가 데이터를 가져오는 방식 = API

학생이 스마트폰으로 매일 쓰는 모든 앱은 결국 서버에 요청을 보내고 응답을 받는 일만 반복합니다.

📖 1. 조회 (GET) — "이 데이터 좀 보여줘"
서버에 있는 정보를 그대로 받아보기만 하는 요청입니다. 쇼핑몰 상품 목록 보기, 뉴스 기사 읽기가 모두 GET입니다.
💾 2. 저장 (POST) — "이 데이터를 서버에 남겨줘"
내가 보낸 내용이 서버 데이터베이스에 새로 기록되는 요청입니다. 회원가입, 장바구니 담기, 관심종목 등록이 POST입니다.
💬 오늘 수업에서 만날 OpenDART는 재무제표를 받아오는 것(GET)이 핵심입니다.
🔄 요청과 응답의 두 가지 갈래 (Tier 3 Visual)
보내는 쪽(클라이언트) ↔ 받는 쪽(서버). 동작은 오직 읽기냐 쓰기냐로 갈립니다.

§200 비즈니스 사례 · 공모전 서버

공모전 관심종목 앱 — 종목 조회는 GET, 관심종목 저장은 POST

💡 실제 서비스에서 두 동작이 쓰이는 장면
금융 데이터 공모전에서 "AI 관심종목 추천 서비스"를 만든다고 가정해 봅시다. 한 화면 안에서 조회와 저장이 동시에 일어납니다.
조회 화면과 저장 버튼이 같은 서버에서 서로 다른 두 동작을 부릅니다.
📌 REST는 딱 한 줄만 기억하면 됩니다
"URL 주소 뒤에 물음표(?)를 달고 조건을 붙여 보내면 정돈된 데이터(JSON)가 돌아오는 약속"
교과서의 복잡한 자원 상태(State Transfer) 이론은 필요 없습니다. 웹 브라우저 주소창에 검색어를 치듯이, URL에 파라미터를 담아 요청하면 서버가 규격화된 표/JSON으로 답해주는 방식이 바로 REST입니다.
우리가 오늘 실습할 OpenDART가 정확히 이 방식(REST API)으로 동작합니다!

§200 서버의 본질 · 클라이언트와 서버

내 컴퓨터도 서버가 될 수 있다 — 요청을 받아 응답하는 프로그램이 떠 있으면 서버다

🏢 서버는 슈퍼컴퓨터가 아니다

많은 초보자들이 "서버"라고 하면 IDC 센터에 있는 수천만 원짜리 초대형 컴퓨터를 떠올립니다. 하지만 서버의 소프트웨어적 본질은 매우 소박합니다.

"포트를 열고, 밖에서 요청이 들어오면 약속된 데이터를 돌려주는 프로그램이 실행 중인 컴퓨터"
학생 노트북에서 파이썬 코드로 포트 하나를 열어두면, 그 순간 내 노트북은 전 세계 누구에게나 응답할 수 있는 서버가 됩니다.
금융감독원 OpenDART 서버도 규모와 트래픽이 클 뿐, "요청을 기다렸다가 재무제표를 돌려준다"는 작동 원리는 똑같습니다.
💻 내 노트북이 서버가 되는 순간
이제 우리는 클라이언트가 되어, 금감원 OpenDART 서버에 직접 요청을 보내봅니다.

§300 DART & OpenDART · 전통 방식

금융감독원 DART — 인증키 신청 5단계와 .env 파일의 보안 원칙

🏛️ DART와 OpenDART 인증키 5단계
상장기업의 공시 서류를 보관하는 전자공시시스템(DART)을 코드로 읽으려면 인증키가 필수입니다.
1 opendart.fss.or.kr 메인 접속
2 상단 메뉴의 인증키 신청/관리 클릭
3 회원가입 약관 동의 및 이메일 인증 (수업 전 완료!)
4 로그인 후 오픈 API 인증키 발급
5 개발가이드에서 단일회사 주요계정 요청 규격 확인
⚠️ 인증키 문자열 자체는 어떤 슬라이드, 노트북 셀, Git 커밋에도 절대 적지 않습니다!
🗂️ 발급받은 키를 .env 파일에 보관하기
키는 코드에 적지 않고, FD_26 프로젝트 루트의 .env 파일에 단 한 줄로 담습니다.
# FD_26 루트의 .env 파일 내용 예시
OPENDART_API_KEY=내_인증키_문자열_붙여넣기
🚨 Windows 사용자의 .env.txt 함정 주의!
윈도우 탐색기에서 새 텍스트 문서를 만들면 파일명이 .env.txt로 숨겨질 위험이 있습니다. 반드시 VS Code 내부에서 직접 New File → .env 로 만드세요.
노트북은 load_dotenv()로 이 파일을 읽으므로 터미널 export는 필요 없습니다.

§300 전통 방식의 고통 · 수작업 파라미터

파라미터 4종을 외워야 하는 번거로움과 30개 행 수동 파싱의 고통

😫 전통적 방식(requests)의 4대 고통
① 파라미터 4종 암기 & 조립
crtfc_key(키), corp_code(종목코드 005930이 아닌 고유번호 00126380), bsns_year(2025), reprt_code(사업보고서 코드 11011). 하나만 틀려도 에러!
② 30개 넘는 계정 행에서 골라내기
응답에 유동자산, 부채 등 30개 행이 쏟아집니다. 그중 fs_div == 'CFS'(연결)인 행을 수동 탐색해야 합니다.
③ 쉼표 문자열 파싱
금액이 콤마가 포함된 문자열이라 replace(',', '') 후 정수 변환 필요.
④ 단위 환산 함정 (원 → 억원)
원 단위 숫자를 1e8로 나눠 억원으로 맞추지 않으면, 지표가 100만 배 왜곡됩니다.
이 모든 수작업을 거쳐 비로소 당기순이익 45.2조 원 / 자본 436.3조 원을 얻었습니다.
🧪 전통 방식의 험난한 파이프라인
"이 고통스러운 과정을 매번 다른 종목마다 반복해야 할까?" → 그래서 MCP가 등장합니다.

§400 MCP · 표준 프로토콜

USB-C 허브처럼, 어디에나 꽂히는 표준 — Model Context Protocol

🔌 왜 USB-C 비유인가?

과거에는 기기마다 충전 단자가 제각각이었습니다(5핀, 8핀, 원형 잭). 하지만 USB-C 규격 하나로 통일된 뒤에는 어떤 기기든 같은 케이블로 연결됩니다.

MCP (Model Context Protocol)
AI 에이전트(Claude, Copilot)가 외부 도구나 데이터베이스에 연결되는 방식을 통일한 오픈 프로토콜 규격입니다.
에이전트에게 일일이 전용 파이썬 API 코드를 짜줄 필요 없이, MCP 서버 하나만 꽂으면 에이전트가 그 도구를 즉시 이해하고 조작합니다.

§500 투자 원칙 · 지표의 한계

PER/PBR/ROE는 판정이 아니라 렌즈 — 단위 혼용(100만 배 함정)과 해석의 경계

🚨 100만 배 함정: 단위를 섞으면 지표가 박살 난다

OpenDART 원본은 원(KRW) 단위 문자열이지만, 우리 DB의 financials는 억원(1e8) 정수로 통일했습니다.

❌ 치명적 실수:
시가총액(401조 원)을 억원으로 안 나누고 원 단위 그대로 둔 채, 당기순이익(452,068 억 원)으로 나누면?
→ PER = 약 887만 배라는 황당한 숫자가 나옵니다!
분자와 분모의 단위를 반드시 억원으로 통일해야 정상적인 8.88배가 나옵니다.
모든 금액 계산 전 단위(원 vs 억원) 체크는 필수 습관!
⚖️ 지표는 필터(스크리닝)일 뿐, 매수 판정이 아니다

PER 8.88배, PBR 0.92배를 보고 "어? 1보다 작고 배수도 낮으니 무조건 사야겠네!"라고 결론내리면 매우 위험합니다.

1. Value Trap (가치 함정): 회사의 업황이 꺾이고 미래 성장성이 없어서 주가가 폭락한 결과 PBR이 낮아진 것일 수 있습니다.
2. 일회성 이익 착시: 부동산 매각 등으로 일시적으로 순이익이 튀어 PER이 낮게 보이는 경우도 있습니다.
지표는 "자세히 살펴볼 후보를 추리는 렌즈"이지, 최종 매수 버튼이 아닙니다.

🔑 Supabase의 3가지 열쇠, 무엇을 어디에 쓰나?
열쇠 종류 쓰는 곳 보관 위치
Secret API key
(sb_secret_...)		 파이썬 create_client로 직접 DB에 쓸 때 .env 파일
OAuth 로그인 에이전트가 MCP로 Supabase를 조작할 때 브라우저 세션 (저장 불필요)
개인 토큰(PAT) 브라우저가 없는 CI/서버 환경 (이번 실습 제외) 필요시 환경변수
SDK는 로컬 secret key로, MCP는 OAuth로 접속합니다. MCP는 프로젝트를 제한하고 실행할 SQL을 먼저 확인합니다.
§610에서 MCP로 표를 만든 뒤 같은 OpenDART 행을 INSERT하고, 이 노트북에서 SDK upsert를 확인합니다.
📌 §600-5 🔍 조회 — 같은 값이 클라우드에도 있는지 확인
OpenDART API 응답으로 만든 payload를 Supabase에 직접 upsert():
SDK는 API 요청을 파이썬 함수로 쉽게 부르게 해주는 코드 묶음입니다. 자연어 MCP는 에이전트에게 말로 도구 실행을 요청합니다.
# §600-4 업로드
supabase.table("financials").upsert(payload, on_conflict="code,year").execute()

# §600-5 클라우드 조회

[오답 해부] Windows 탐색기의 .env.txt 함정과 CFS(연결) vs OFS(별도) 혼동

❌ 오답 1: Windows 탐색기의 .env.txt 숨김 참사

"분명히 .env 파일을 만들고 키를 넣었는데, 파이썬이 키를 못 찾아요!"

원인: 윈도우 기본 설정에서 "알려진 파일 형식의 확장명 숨기기"가 켜져 있으면, 메모장으로 저장한 파일의 실제 이름은 .env.txt가 됩니다!
✅ 해결책: 윈도우 탐색기에서 만들지 말고, VS Code 왼쪽 탐색기에서 직접 New File → .env 로 생성하세요.
VS Code는 점(.)으로 시작하는 파일 확장자를 정확히 다룹니다.
❌ 오답 2: CFS(연결) 대신 OFS(별도)를 집는 실수

"당기순이익 숫자가 교재랑 달라요! 왜 저는 30조 원대가 나오죠?"

원인: OpenDART 응답에는 CFS(자회사 포함 연결)와 OFS(본체만 별도) 행이 둘 다 있습니다. 필터 없이 위에서부터 첫 행을 집으면 별도 기준 숫자를 집게 됩니다!
✅ 해결책: 반드시 if row['fs_div'] == 'CFS' 조건을 걸어 연결 기준 45.2조 원을 선택해야 합니다.
대기업 재무제표의 기본 표준은 언제나 연결(CFS) 기준입니다.

[오답 해부] 원과 억원을 섞으면 PER이 8.88이 아니라 약 887만 배가 된다

💥 왜 100만 배 차이가 발생하는가?

금융 데이터 분석에서 가장 흔하면서도 치명적인 버그가 바로 단위 불일치(Unit Mismatch)입니다.

1. OpenDART API: 원 단위 (1원)
2. SQLite financials 테이블: 억원 단위 (100,000,000원 = 1e8)
3. 주가 × 주식수 (시총 원본): 원 단위 (1원)
시총을 1e8로 나누지 않고 당기순이익(억원)으로 나누면 100,000,000 ÷ 1 = 1억 배가 아니라 100만 배 왜곡이 일어납니다!
📏 올바른 계산 공식과 단위 변환 규칙
# 1. 시가총액 계산 시 반드시 1e8로 나눈다
market_cap_eok = (close_price * shares) / 1e8
# 결과: 4,012,567 억 원

# 2. 억원끼리 나누면 완벽한 배수가 도출된다
per = market_cap_eok / net_income_eok
# 4,012,567 ÷ 452,068 = 8.88 배 (정상!)
상식적으로 생각해도 삼성전자 PER이 800만 배일 수는 없습니다. 계산 결과가 비상식적으로 크다면 100% 단위 변환 문제입니다.
공식 외우기보다 "둘 다 억원으로 맞췄는가?"를 먼저 점검하세요!
